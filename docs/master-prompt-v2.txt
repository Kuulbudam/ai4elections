2. PROJECT BACKGROUND

AI4Elections is an electoral data intelligence, data validation, statistical anomaly detection and evidence management platform.

Its purpose is to help authorised election analysts and researchers:

* Upload aggregated election result datasets.
* Preserve original data and establish provenance.
* Validate electoral result data.
* Identify inconsistencies and unusual statistical patterns.
* Compare polling units and administrative areas.
* Investigate findings using source evidence.
* Record human review decisions.
* Generate reproducible analytical reports.

The central workflow is:

UPLOAD → PRESERVE → VALIDATE → ANALYSE → INVESTIGATE → REVIEW → REPORT

The initial target is a working MVP for a hackathon demonstration in December 2026 (the Rise Networks #AI4Elections Hackathon). As of 18 November 2026 this leaves only a few weeks. Section 11 defines a "demo-critical path" that must be protected; everything outside it is cut first if time runs short.

What AI4Elections is NOT

It is not:

* An electronic voting system.
* A vote-counting system.
* A result transmission system.
* An election certification platform.
* An automated fraud detection or fraud verdict system.

A statistical anomaly is an investigation signal, not proof of fraud or wrongdoing.

The platform must clearly separate: data quality issues, statistical anomalies, unverified allegations, and independently verified facts (see Section 5.7).

5.4 Canonical data model (schema version 1.0.0)

Canonical fields:

* pu_code (required, text)
* state (required, text)
* lga (required, text)
* ward (required, text)
* registered_voters (required, integer ≥ 0)
* accredited_voters (required, integer ≥ 0)
* valid_votes (required, integer ≥ 0)
* rejected_votes (required, integer ≥ 0)
* total_cast (required, integer ≥ 0; expected to equal valid_votes + rejected_votes)
* latitude, longitude (optional, decimal; must be supplied together)

Party vote columns are mapped dynamically (column → party code) and stored as a validated JSON object of {party_code: integer ≥ 0}. At least two party columns are required for share analysis.

The canonical schema is versioned; each result record stores the schema version it was built with.

Synthetic data note: all coordinates in development data are synthetic and must be labelled as such everywhere they appear.

5.5 Data validation

Deterministic rules (rule IDs are stable; tolerance for equality checks is 0 by default and is a versioned rule parameter):

V001 Required columns present and mapped.
V002 Duplicate column assignments in the mapping.
V003 Missing required value in a row (includes missing pu_code).
V004 Invalid numeric value (non-integer, text, decimals where integers are required).
V005 Negative value.
V006 accredited_voters > registered_voters.
V007 Vote reconciliation: total_cast ≠ valid_votes + rejected_votes, or total_cast > accredited_voters.
V008 Sum of party votes ≠ valid_votes.
V009 Count exceeds its denominator: valid_votes > total_cast, rejected_votes > total_cast, any party vote > valid_votes.
V010 Duplicate pu_code within a dataset version.
V011 Unmatched administrative label (state/LGA/ward not in the project's reference list, or ward listed under more than one LGA). If no reference list is loaded, this rule reports "not evaluated" rather than passing.
V012 Invalid coordinates (only one of the pair, out of range, or outside the country's bounding box when one is configured).

Each rule has: rule ID, version, severity (info / warning / error), classification (structural / completeness / arithmetic / consistency / identity / geography), description, affected fields, remediation guidance.

Each validation issue stores: dataset version, raw row ID, source row number, source column name, original cell text, rule ID + version.

Row statuses:

* eligible — no issues.
* eligible_with_warnings — only warning/info issues.
* quarantined_from_specific_analysis — has error issues; the row stores which indicators it is excluded from and why (for example: V004 on registered_voters → excluded from turnout, still usable for vote share if its vote fields are clean).

Quarantine must be explained in plain language and limited to the calculations actually affected. Rows with V010 duplicate pu_code are excluded from all statistical indicators until resolved.

5.6 Statistical analysis (method version 1.0.0)

Indicators:

* Turnout rate = accredited_voters / registered_voters (not computed if registered_voters = 0).
* Leading-party vote share = highest party vote / valid_votes (not computed if valid_votes = 0).

Peer groups:

* Default: polling units in the same ward (same state + LGA + ward).
* Fallback: polling units in the same LGA, used only when the ward group is too small. The finding must record that the fallback was used.
* Minimum peer group size: n ≥ 10 eligible units (parameter, versioned). Below that at both levels: no score, the unit is listed as "not scored — insufficient peers".
* The unit being scored is included in the peer group median calculation; record this choice in the methodology.

Method:

Median = median(x)
MAD = median(|xᵢ − Median|)
robust_z = 0.6745 × (x − Median) / MAD

* Flag when |robust_z| ≥ 3.5 (Iglewicz–Hoaglin threshold; versioned parameter).
* If MAD = 0: do not compute a score. Record "not scored — zero MAD". Never substitute an invented score.
* Turnout above 100% is a validation error (V006), not a statistical finding.

Severity (how unusual): based on |robust_z| bands — 3.5 to <5 = medium, 5 to <7 = high, ≥7 = very high.
Confidence (how much we trust the signal): high when peer group is ward-level with n ≥ 20 and the row is eligible; medium when n is 10–19 or LGA fallback was used; low when the row is eligible_with_warnings. Severity and confidence are stored separately and never combined into one score.

Every finding stores: dataset version, analysis run, engine version, method version, indicator, peer group level and key, sample size, exclusions (with reasons), median, MAD, robust_z (or null with reason), threshold used, severity, confidence, evidence (the source row values and raw row reference), and a limitations text.

Determinism: given the same dataset version, mapping, rule versions and method version, an analysis run must produce identical findings (same values, same order, same content hash).

No machine-learning anomaly models in the MVP.

8. JOB PROCESSING AND RELIABILITY

PostgreSQL is the durable job ledger.

States: queued → running → succeeded | failed (plus cancelled, optional).

Store: job type, org_id, project_id, target IDs, input fingerprint, attempt_count, max_attempts, created_at, started_at, finished_at, heartbeat_at, progress, safe error code, retryable flag, worker ID.

Implement:

* Atomic job claiming (SELECT … FOR UPDATE SKIP LOCKED inside a transaction, or an equivalent claim function).
* Idempotent processing: a unique key on (job type, target, input fingerprint) prevents duplicate jobs; outputs are written inside one transaction keyed by run ID, so a retry replaces its own partial output and never duplicates raw rows, issues or findings.
* Safe retries with a maximum attempt count.
* Stale-job reconciliation: a running job whose heartbeat is older than a set time is returned to queued (if attempts remain) or marked failed.
* Worker-side verification: before processing, the worker re-checks that the job's org_id, project_id and target IDs belong together.
* A failed job never appears as succeeded. An analytical run is only marked complete after all its findings are committed.

90-second worker spike (Phase 0, on the chosen hosting option): a dummy job that runs ~90 seconds with heartbeats, then tests: (1) normal completion and persistence, (2) forced timeout/kill mid-run → reconciliation and retry, (3) duplicate dispatch → only one execution, (4) cost observed (should be $0). Record results in docs.

Do not activate always-on paid services without approval.
